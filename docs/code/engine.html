 122 ---------------------
 123 Like Module 1, this module is intentionally designed around month-level history rather than
 124 treating PHP strings as the computational backbone.

 126 This means:
 127 - We use module1.metro2_status_history as the truth source

 165 4) CURE POLICY NOTE
 166    The 3-month cure rule is a conservative remediation-policy default used for this analytical
 167    framework. It is not presented here as a formal Metro 2 requirement.
 168 
 169    In this module:
 170    - Cure means N consecutive months of status = '0'
 171    - Cure is evaluated AFTER impact_end_date
 172    - B and D do NOT count as cure
 173    - Only literal 0 counts as cure
 174 
 175 5) IMPORTANT DIFFERENCE BETWEEN FINANCIAL IMPACT AND CREDIT IMPACT
 176    Financial impact dates:
 177       - impact_start_date
 178       - impact_end_date
 179 
 180    Credit impact dates:
 181       - credit_impact_start_date
 182       - credit_impact_end_date
 183 
 184    In this module:
 185    - credit_impact_start_date = impact_start_date
 186    - credit_impact_end_date may extend beyond impact_end_date because we allow time for the
 187      customer to stabilize from a credit reporting standpoint
 188 
 189 6) MANUAL REVIEW POLICY
 190    Manual review is intended to identify accounts where impact may still be ongoing.
 191 
 192    In this module:
 193    - If an account is closed and there is no cure, do NOT manual review
 194    - If an account is open and has insufficient post-impact months, manual review may be needed
 195    - If an account is open and no cure is found, manual review may be needed
 196    - HOWEVER: if there is no delinquency and no derogatory content in the credit impact timeframe,
 197      there is no impact to remediate and no manual review is needed
 198 
 199 7) DELETION OVERRIDE POLICY
 200    Tradeline deletion is the most conservative remediation treatment in this module.
 201 
 202    Find the latest original G/H/J/K/L inside the inclusive credit-impact window.
 203    Look for the first original 0–6 strictly after it. This synthetic observation
 204    supports reversal even if the account is still delinquent and cure is unconfirmed.
 205    Without reversal, propose whole-tradeline deletion (DA). With reversal, retain
 206    the tradeline and target its eligible in-window months. A new severe event in
 207    that same window requires fresh reversal evidence; B and D supply none.
 208 
 209    The cure test uses only consecutive original zeros strictly after bank impact.
 210    Once confirmed, the window closes just before the first qualifying zero. Isolated
 211    later events belong to separate assessment. An operational reversal should be
 212    substantiated by the relevant account and event records.
 213 
 214    Deletion is an account-level instruction. The original monthly evidence remains
 215    visible and the final manual-review flag is zero.
 216 
 217 8) HOW REMEDIATED PHP WORKS
 218    FULL_DEROGATORY_PHP_CLEANUP:
 219       - inside the credit impact timeframe only
 220       - suppress 1-6 and G/H/J/K/L to D
 221 
 222    SIMPLE_DELINQUENCY_PHP_CLEANUP:
 223       - inside the credit impact timeframe only
 224       - suppress 1-6 to D
 225 
 226    TRADELINE_DELETION:
 227       - no remediated PHP string is populated
 228 
 229    NO_IMPACT_CLEAN_PHP_HISTORY:
 230       - remediated PHP remains NULL because no change was made
 231 
 232 9) IMPORTANT REMEDIATED DERIVATION RULE
 233    PHP byte 1 covers the month before DOAI. Field 17A is current as of DOAI. For the
 234    synthetic election, an adverse-to-D correction to the newest month must be corroborated
 235    by its as-of status and field evidence. Otherwise preserve the current fields. For a
 236    closed account, check the specific paid-derogatory or pre-closure rating basis. Source
 237    D supplies no new onset. Cure still requires consecutive original post-issue zeros.
 238    Consumer Information Indicators (CII) and the associated Field 25 exceptions are
 239    outside these inputs. Internal SQL dates and clear flags describe study actions.
 240 
 241 10) DELTA-BASED OUTPUT DESIGN
 242    Remediated fields are only populated when a change is actually made.
 243 
 244    That means:
 245    - if remediated_full_php is unchanged, it stays NULL
 246    - if remediated_account_status_17A is unchanged, it stays NULL
 247    - a populated remediated field supplies its replacement value
 248    - clear_account_status_17a, clear_payment_rating_17b and clear_date_of_first_delinquency
 249      separately identify a cleanup instruction to set an existing field to NULL
 250    - otherwise keep the original value. A deletion supplies DA only.

 429 -- ====================================================================================================
 430 -- Check the source grain before resetting outputs. Cure is measured in calendar months.
 431 -- An omitted or duplicated month would break the relationship between byte position and date.
 432 DO $$
 433 BEGIN
 434     IF NOT EXISTS (SELECT 1 FROM module1.metro2_final)
 435        OR EXISTS (
 436            SELECT 1 FROM module1.metro2_final
 437            GROUP BY account HAVING account IS NULL OR count(*) <> 1
 438        ) THEN
 439         RAISE EXCEPTION 'MODULE 2 INPUT VALIDATION FAILED: expected one original summary per account and a nonempty population.';
 440     END IF;
 441 
 442     IF EXISTS (
 443         WITH monthly AS (
 444             SELECT account, min(byte_date) AS first_month, max(byte_date) AS last_month,
 445                    count(*) AS months, count(DISTINCT byte_date) AS unique_dates,
 446                    bool_or(byte_date IS NULL OR extract(day FROM byte_date) <> 1
 447                        OR status IS NULL OR status NOT IN ('0','1','2','3','4','5','6','B','D','G','H','J','K','L')) AS invalid_month,
 448                    string_agg(status, '' ORDER BY byte_date DESC) AS full_php
 449             FROM module1.metro2_status_history
 450             GROUP BY account
 451         )
 452         SELECT 1
 453         FROM module1.metro2_final f
 454         FULL JOIN monthly m USING (account)
 455         WHERE f.account IS NULL OR m.account IS NULL OR m.invalid_month
 456            OR f.php_right_byte_date IS DISTINCT FROM m.first_month
 457            OR f.php_left_byte_date IS DISTINCT FROM m.last_month
 458            -- This simulator reports on the first of the following month. Future PHP
 459            -- cannot close the present review. B can only pad the oldest end of history.
 460            OR f.latest_doai IS DISTINCT FROM (m.last_month + interval '1 month')::date
 461            OR m.full_php !~ '^[0-6DGHJKL]*B*$'
 462            OR f.full_php IS DISTINCT FROM m.full_php
 463            OR m.months <> m.unique_dates
 464            OR m.months <> (12 * (extract(year FROM m.last_month) - extract(year FROM m.first_month))
 465                             + extract(month FROM m.last_month) - extract(month FROM m.first_month) + 1)
 466     ) THEN
 467         RAISE EXCEPTION 'MODULE 2 INPUT VALIDATION FAILED: monthly source and summary must agree on account, monthly grain, inclusive endpoints and newest-first PHP. DOAI must be the next month-start; supported marks are 0-6/D/G/H/J/K/L and B only before all reported history.';
 468     END IF;
 469 END $$;

 472 -- Hold them in this transaction before replacing outputs. A bad or incomplete prior cohort

 482            OR to_regclass('module2.metro2_remediation_window_eval') IS NULL
 483            OR to_regclass('module2.metro2_remediation_final') IS NULL THEN
 484             RAISE EXCEPTION 'MODULE 2 INCIDENT REUSE FAILED: prior input, window and final tables are required.';
 485         END IF;
 486         LOCK TABLE module2.metro2_remediation_input, module2.metro2_remediation_window_eval,
 487                    module2.metro2_remediation_final IN SHARE ROW EXCLUSIVE MODE;
 488         INSERT INTO pg_temp.module2_saved_incident_dates
 489         SELECT account, impact_start_date, impact_end_date FROM module2.metro2_remediation_input;
 490 
 491         IF EXISTS (
 492             SELECT 1 FROM pg_temp.module2_saved_incident_dates
 493             GROUP BY account HAVING account IS NULL OR count(*) <> 1
 494         ) OR EXISTS (
 495             SELECT 1 FROM module1.metro2_final f
 496             FULL JOIN pg_temp.module2_saved_incident_dates i USING (account)
 497             WHERE i.account IS NULL OR f.account IS NULL
 498                OR i.impact_start_date IS NULL OR i.impact_end_date IS NULL
 499                OR extract(day FROM i.impact_start_date) <> 1 OR extract(day FROM i.impact_end_date) <> 1

 503             RAISE EXCEPTION 'MODULE 2 INCIDENT REUSE FAILED: expected the same accounts and one valid, represented month-start bank date pair per account.';

 524             RAISE EXCEPTION 'MODULE 2 INCIDENT REUSE FAILED: the configured cure threshold must match both saved thresholds for every account. Use the original configured Module 2 for follow-up or create a separate study.';

 561 -- ====================================================================================================
 562 -- SECTION 4: BUILD REMEDIATION INPUT TABLE
 563 -- ====================================================================================================
 564 -- Purpose:
 565 --   Simulate the second input table:
 566 --      - account
 567 --      - impact_start_date
 568 --      - impact_end_date
 569 --
 570 -- Why this exists:
 571 --   Module 2 needs a bank-side remediation timeframe input.
 572 --   We simulate it deterministically so the same account gets the same input every run.
 573 --
 574 -- Important rule:
 575 --   impact_start_date and impact_end_date must fall within the represented PHP history:
 576 --      - between php_right_byte_date and php_left_byte_date
 577 --
 578 -- SQL mechanics:
 579 --   - Pull each account's available history window from module1.metro2_final
 580 --   - Use deterministic hashed seeds to choose a valid start offset and duration
 581 --   - This mirrors the reproducible synthetic style used in Module 1
 582 -- ====================================================================================================
 583 CREATE TABLE module2.metro2_remediation_input AS
 584 WITH
 585 base AS (
 586     SELECT
 587         f.account,
 588         f.php_right_byte_date,
 589         f.php_left_byte_date,
 590         (
 591             EXTRACT(YEAR  FROM age(f.php_left_byte_date, f.php_right_byte_date)) * 12
 592           + EXTRACT(MONTH FROM age(f.php_left_byte_date, f.php_right_byte_date))
 593         )::INT + 1 AS history_month_count
 594     FROM module1.metro2_final f
 595     WHERE NOT EXISTS (SELECT 1 FROM pg_temp.module2_saved_incident_dates)
 596 ),
 597 seeds AS (
 598     SELECT
 599         b.*,
 600         (('x' || substr(md5(account::text || '-m2a'), 1, 7))::bit(28)::int) AS s1,
 601         (('x' || substr(md5(account::text || '-m2b'), 1, 7))::bit(28)::int) AS s2
 602     FROM base b
 603 ),
 604 offsets AS (
 605     SELECT
 606         account,
 607         php_right_byte_date,
 608         php_left_byte_date,
 609         history_month_count,
 610         (s1 % history_month_count) AS start_offset
 611     FROM seeds
 612 ),
 613 durations AS (
 614     SELECT
 615         o.*,
 616         (('x' || substr(md5(o.account::text || '-m2c'), 1, 7))::bit(28)::int) AS s3
 617     FROM offsets o
 618 ),
 619 final_input AS (
 620     SELECT
 621         d.account,
 622         (d.php_right_byte_date + ((d.start_offset) * INTERVAL '1 month'))::DATE AS impact_start_date,
 623         (
 624             d.php_right_byte_date
 625             + ((d.start_offset) * INTERVAL '1 month')
 626             + (
 627                 (
 628                     (d.s3 % GREATEST(d.history_month_count - d.start_offset, 1))
 629                 ) * INTERVAL '1 month'
 630               )
 631         )::DATE AS impact_end_date
 632     FROM durations d
 633 )
 634 SELECT
 635     account,
 636     impact_start_date,
 637     impact_end_date
 638 FROM final_input
 639 UNION ALL
 640 SELECT account, impact_start_date, impact_end_date
 641 FROM pg_temp.module2_saved_incident_dates
 642 ORDER BY account;

 681 -- ====================================================================================================
 682 -- SECTION 6: BUILD LAYER 1 WINDOW EVALUATION TABLE
 683 -- ====================================================================================================
 684 -- Purpose:
 685 --   Establish the credit-impact timeframe and treatment logic.
 686 --
 687 -- This section determines:
 688 --   - credit_impact_start_date
 689 --   - credit_impact_end_date
 690 --   - credit_cure_date
 691 --   - manual_review_flag
 692 --   - manual_review_reason
 693 --   - remediation_treatment
 694 --
 695 -- Major business rules implemented here:
 696 --   1) credit_impact_start_date = impact_start_date
 697 --   2) cure requires N consecutive months of status = '0' AFTER impact_end_date
 698 --   3) if no cure and closed, do not manual review
 699 --   4) if no cure and open, manual review may depend on post-impact history sufficiency
 700 --   5) if there is no delinquency and no derogatory content in the credit impact timeframe,
 701 --      then there is no impact to remediate and no manual review is needed
 702 --   6) the latest in-window G/H/J/K/L requires deletion until original later 0–6 supports reversal
 703 --   7) reversal supports targeted cleanup; the separate cure test determines ongoing exposure
 704 -- ====================================================================================================
 705 CREATE TABLE module2.metro2_remediation_window_eval AS
 706 WITH
 707 -- --------------------------------------------------------------------------------------------
 708 -- CTE: base
 709 -- Purpose:
 710 --   Combine Module 1 account-level context with the simulated remediation input and parameter row.
 711 --
 712 -- Why this exists:
 713 --   This creates the account-level foundation for all later Layer 1 logic.
 714 --
 715 -- SQL mechanics:
 716 --   - Join module1.metro2_final to metro2_remediation_input by account
 717 --   - Cross join the one-row parameter table
 718 --   - Derive a closed-account flag from 17A
 719 -- --------------------------------------------------------------------------------------------
 720 base AS (
 721     SELECT
 722         f.account,
 723         f.profile_type,
 724         f.latest_doai,
 725         f.date_closed,
 726         f.full_php,
 727         f.php_left_byte_date,
 728         f.php_right_byte_date,
 729         f.account_status_17A,
 730         f.payment_rating_17B,
 731         f.date_of_first_delinquency,
 732         i.impact_start_date,
 733         i.impact_end_date,
 734         p.cure_consecutive_months_required,
 735         CASE
 736             WHEN f.account_status_17A IN ('13','61','62','63','64','65') THEN 1
 737             ELSE 0
 738         END AS is_closed_account
 739     FROM module1.metro2_final f
 740     JOIN module2.metro2_remediation_input i
 741       ON f.account = i.account
 742     CROSS JOIN pg_temp.module2_params p
 743 ),
 744 
 745 -- --------------------------------------------------------------------------------------------
 746 -- CTE: post_impact_months
 747 -- Purpose:
 748 --   Pull all month-level statuses strictly AFTER impact_end_date.
 749 --
 750 -- Why this exists:
 751 --   Cure is defined using post-impact months only.
 752 --
 753 -- SQL mechanics:
 754 --   - Join to module1.metro2_status_history
 755 --   - Keep only byte_date > impact_end_date
 756 --   - Sequence months from oldest to newest using ROW_NUMBER
 757 -- --------------------------------------------------------------------------------------------
 758 post_impact_months AS (
 759     SELECT
 760         b.account,
 761         h.byte_date,
 762         h.status,
 763         ROW_NUMBER() OVER (
 764             PARTITION BY b.account
 765             ORDER BY h.byte_date
 766         ) AS seq_asc
 767     FROM base b
 768     JOIN module1.metro2_status_history h
 769       ON b.account = h.account
 770     WHERE h.byte_date > b.impact_end_date
 771 ),
 772 
 773 -- --------------------------------------------------------------------------------------------
 774 -- CTE: post_impact_counts
 775 -- Purpose:
 776 --   Count how many represented months exist after impact_end_date.
 777 --
 778 -- Why this exists:
 779 --   We need to know whether the account has enough post-impact months to evaluate cure.
 780 -- --------------------------------------------------------------------------------------------
 781 post_impact_counts AS (
 782     SELECT
 783         account,
 784         COUNT(*) AS post_impact_month_count
 785     FROM post_impact_months
 786     GROUP BY account
 787 ),
 788 
 789 -- --------------------------------------------------------------------------------------------
 790 -- CTE: zero_only
 791 -- Purpose:
 792 --   Keep only post-impact months with status = '0'.
 793 --
 794 -- Why this exists:
 795 --   In this framework, cure is strict:
 796 --      only literal 0 counts
 797 --      B and D do not count
 798 --
 799 -- SQL mechanics:
 800 --   - seq_asc - row_number() is a classic SQL technique for identifying consecutive runs
 801 -- --------------------------------------------------------------------------------------------
 802 zero_only AS (
 803     SELECT
 804         account,
 805         byte_date,
 806         seq_asc,
 807         seq_asc - ROW_NUMBER() OVER (
 808             PARTITION BY account
 809             ORDER BY byte_date
 810         ) AS zero_grp
 811     FROM post_impact_months
 812     WHERE status = '0'
 813 ),
 814 
 815 -- --------------------------------------------------------------------------------------------
 816 -- CTE: zero_runs
 817 -- Purpose:
 818 --   Collapse consecutive zero rows into runs and measure each run's length.
 819 -- --------------------------------------------------------------------------------------------
 820 zero_runs AS (
 821     SELECT
 822         account,
 823         zero_grp,
 824         MIN(byte_date) AS run_start_date,
 825         MAX(byte_date) AS run_end_date,
 826         COUNT(*) AS run_length
 827     FROM zero_only
 828     GROUP BY account, zero_grp
 829 ),
 830 
 831 -- --------------------------------------------------------------------------------------------
 832 -- CTE: qualifying_cure
 833 -- Purpose:
 834 --   Find the earliest zero run that satisfies the configured cure threshold.
 835 --
 836 -- Definition:
 837 --   credit_cure_date = first month of the first qualifying cure run
 838 -- --------------------------------------------------------------------------------------------
 839 qualifying_cure AS (
 840     SELECT DISTINCT ON (z.account)
 841         z.account,
 842         z.run_start_date AS credit_cure_date
 843     FROM zero_runs z
 844     JOIN pg_temp.module2_params p
 845       ON 1 = 1
 846     WHERE z.run_length >= p.cure_consecutive_months_required
 847     ORDER BY z.account, z.run_start_date
 848 ),
 849 
 850 -- --------------------------------------------------------------------------------------------
 851 -- CTE: preliminary_eval
 852 -- Purpose:
 853 --   Apply the basic Layer 1 credit-impact end-date logic BEFORE treatment assignment.
 854 --
 855 -- Rules:
 856 --   - If cure found:
 857 --       credit_impact_end_date = month before cure date
 858 --       manual_review_flag_pre = 0
 859 --   - Else if closed:
 860 --       credit_impact_end_date = php_left_byte_date
 861 --       manual_review_flag_pre = 0
 862 --   - Else if insufficient post-impact months:
 863 --       credit_impact_end_date = php_left_byte_date
 864 --       manual_review_flag_pre = 1
 865 --       reason = INSUFFICIENT_POST_IMPACT_HISTORY
 866 --   - Else:
 867 --       credit_impact_end_date = php_left_byte_date
 868 --       manual_review_flag_pre = 1
 869 --       reason = NO_CURE_OPEN_ACCOUNT
 870 -- --------------------------------------------------------------------------------------------
 871 preliminary_eval AS (
 872     SELECT
 873         b.account,
 874         b.profile_type,
 875         b.latest_doai,
 876         b.date_closed,
 877         b.full_php,
 878         b.php_left_byte_date,
 879         b.php_right_byte_date,
 880         b.account_status_17A,
 881         b.payment_rating_17B,
 882         b.date_of_first_delinquency,
 883         b.impact_start_date,
 884         b.impact_end_date,
 885         b.cure_consecutive_months_required,
 886         b.is_closed_account,
 887 
 888         b.impact_start_date AS credit_impact_start_date,
 889         qc.credit_cure_date,
 890 
 891         COALESCE(pc.post_impact_month_count, 0) AS post_impact_month_count,
 892 
 893         CASE
 894             WHEN qc.credit_cure_date IS NOT NULL
 895                 THEN (qc.credit_cure_date - INTERVAL '1 month')::DATE
 896             ELSE b.php_left_byte_date
 897         END AS credit_impact_end_date_pre,
 898 
 899         CASE
 900             WHEN qc.credit_cure_date IS NOT NULL THEN 0
 901             WHEN b.is_closed_account = 1 THEN 0
 902             WHEN COALESCE(pc.post_impact_month_count, 0) < b.cure_consecutive_months_required THEN 1
 903             ELSE 1
 904         END AS manual_review_flag_pre,
 905 
 906         CASE
 907             WHEN qc.credit_cure_date IS NOT NULL THEN NULL
 908             WHEN b.is_closed_account = 1 THEN NULL
 909             WHEN COALESCE(pc.post_impact_month_count, 0) < b.cure_consecutive_months_required
 910                 THEN 'INSUFFICIENT_POST_IMPACT_HISTORY'
 911             ELSE 'NO_CURE_OPEN_ACCOUNT'
 912         END AS manual_review_reason_pre
 913     FROM base b
 914     LEFT JOIN qualifying_cure qc
 915       ON b.account = qc.account
 916     LEFT JOIN post_impact_counts pc
 917       ON b.account = pc.account
 918 ),
 919 
 920 -- --------------------------------------------------------------------------------------------
 921 -- CTE: credit_window_flags
 922 -- Purpose:
 923 --   Inspect the provisional credit impact window and detect whether it contains:
 924 --   - any derogatory bytes (G/H/J/K/L)
 925 --   - any delinquency bytes (1-6)
 926 --   - any original charge-off (L), including when another major event occurs later
 927 --
 928 -- Why this exists:
 929 --   The latest original severe event controls treatment. The any-charge-off flag
 930 --   provides descriptive continuity with earlier study outputs.
 931 --
 932 --   If the credit impact window contains neither delinquency nor derogatory content,
 933 --   then the account is effectively "no impact" from a credit reporting standpoint,
 934 --   even if post-impact history is short.
 935 -- --------------------------------------------------------------------------------------------
 936 credit_window_flags AS (
 937     SELECT
 938         p.account,
 939         MAX(h.byte_date) FILTER (WHERE h.status IN ('G','H','J','K','L')) AS last_severe_month,
 940         MAX(CASE WHEN h.status = 'L' THEN 1 ELSE 0 END) AS has_chargeoff_in_credit_window,
 941         MAX(CASE WHEN h.status IN ('1','2','3','4','5','6') THEN 1 ELSE 0 END) AS has_delinquency_in_credit_window
 942     FROM preliminary_eval p
 943     JOIN module1.metro2_status_history h
 944       ON p.account = h.account
 945      AND h.byte_date BETWEEN p.credit_impact_start_date AND p.credit_impact_end_date_pre
 946     GROUP BY p.account
 947 ),
 948 
 949 -- --------------------------------------------------------------------------------------------
 950 -- A numeric mark before the latest severe event cannot reverse that later event.
 951 -- The first qualifying numeric mark may be the first zero of the cure run. Measure
 952 -- only through its confirmation, or through the latest original month if still open.
 953 -- --------------------------------------------------------------------------------------------
 954 reversal AS (
 955     SELECT f.account, MIN(h.byte_date) AS severe_reversal_month
 956     FROM credit_window_flags f
 957     JOIN preliminary_eval p USING (account)
 958     JOIN module1.metro2_status_history h
 959       ON h.account = f.account
 960      AND h.byte_date > f.last_severe_month
 961      AND h.byte_date <= coalesce(
 962          (p.credit_cure_date + (p.cure_consecutive_months_required - 1) * interval '1 month')::date,
 963          p.php_left_byte_date)
 964      AND h.status IN ('0','1','2','3','4','5','6')
 965     GROUP BY f.account
 966 ),
 967 
 968 -- A reversed severe event gets targeted cleanup. Cure and open/closed status govern
 969 -- the separate review flag, so the same account may receive cleanup and continued review.
 970 treatment_eval AS (
 971     SELECT
 972         p.*,
 973         f.last_severe_month,
 974         r.severe_reversal_month,
 975         (f.last_severe_month IS NOT NULL)::int AS has_derog_in_credit_window,
 976         COALESCE(f.has_chargeoff_in_credit_window, 0) AS has_chargeoff_in_credit_window,
 977         COALESCE(f.has_delinquency_in_credit_window, 0) AS has_delinquency_in_credit_window,
 978         (r.severe_reversal_month IS NOT NULL)::int AS has_post_derog_recovery_evidence,
 979         CASE
 980             WHEN f.last_severe_month IS NOT NULL AND r.severe_reversal_month IS NULL
 981                 THEN 'TRADELINE_DELETION'
 982             WHEN f.last_severe_month IS NOT NULL
 983                 THEN 'FULL_DEROGATORY_PHP_CLEANUP'
 984             WHEN f.has_delinquency_in_credit_window = 1
 985                 THEN 'SIMPLE_DELINQUENCY_PHP_CLEANUP'
 986             ELSE 'NO_IMPACT_CLEAN_PHP_HISTORY'
 987         END AS remediation_treatment
 988     FROM preliminary_eval p
 989     LEFT JOIN credit_window_flags f ON p.account = f.account
 990     LEFT JOIN reversal r ON p.account = r.account
 991 )
 992 
 993 SELECT
 994     account,
 995     profile_type,
 996     latest_doai,
 997     date_closed,
 998     full_php,
 999     php_left_byte_date,
1000     php_right_byte_date,
1001     account_status_17A,
1002     payment_rating_17B,
1003     date_of_first_delinquency,
1004     impact_start_date,
1005     impact_end_date,
1006     credit_impact_start_date,
1007     credit_impact_end_date_pre AS credit_impact_end_date,
1008     credit_cure_date,
1009     cure_consecutive_months_required,
1010     post_impact_month_count,
1011     has_derog_in_credit_window,
1012     has_delinquency_in_credit_window,
1013     has_post_derog_recovery_evidence,
1014     CASE WHEN remediation_treatment IN ('TRADELINE_DELETION', 'NO_IMPACT_CLEAN_PHP_HISTORY')
1015          THEN 0 ELSE manual_review_flag_pre END AS manual_review_flag,
1016     CASE WHEN remediation_treatment IN ('TRADELINE_DELETION', 'NO_IMPACT_CLEAN_PHP_HISTORY')
1017          THEN NULL ELSE manual_review_reason_pre END AS manual_review_reason,
1018     remediation_treatment,
1019     has_chargeoff_in_credit_window,
1020     last_severe_month,
1021     severe_reversal_month,
1022     'REVERSAL_AWARE_SEVERE_V2'::text AS remediation_policy
1023 FROM treatment_eval
1024 ORDER BY account;
1025 
1026 CREATE INDEX ix_remediation_window_eval_account
1027     ON module2.metro2_remediation_window_eval (account);

1031 -- SECTION 7: BUILD MONTH-LEVEL REMEDIATION DETAIL

1033 -- Purpose:
1034 --   Create one row per account per represented month showing:
1035 --   - original status
1036 --   - whether the month is inside the credit impact window
1037 --   - remediated status after treatment logic is applied
1038 --
1039 -- Why this exists:
1040 --   This table is the easiest place to:
1041 --   - inspect exactly which months changed
1042 --   - stitch remediated_full_php later
1043 --   - support future audit and QA work
1044 --
1045 -- SQL mechanics:
1046 --   - Join the Layer 1 result to module1.metro2_status_history
1047 --   - Apply cleanup logic only inside the credit impact timeframe
1048 -- ====================================================================================================

1058         ELSE 0
1059     END AS is_within_credit_impact_window,
1060 
1061     e.remediation_treatment,
1062 
1063     CASE
1064         WHEN e.remediation_treatment = 'FULL_DEROGATORY_PHP_CLEANUP'
1065          AND h.byte_date BETWEEN e.credit_impact_start_date AND e.credit_impact_end_date

1085 -- ====================================================================================================
1086 -- SECTION 8: BUILD FINAL REMEDIATION OUTPUT
1087 -- ====================================================================================================
1088 -- Purpose:
1089 --   Produce the final Module 2 output table with:
1090 --   - original context
1091 --   - impact dates
1092 --   - remediation treatment
1093 --   - remediated delta fields
1094 --   - audit flags
1095 --
1096 -- This section also derives:
1097 --   - remediated_account_status_17A
1098 --   - remediated_payment_rating_17B
1099 --   - remediated_date_of_first_delinquency
1100 --
1101 -- Important design rule:
1102 --   Remediated fields are delta-based.
1103 --   If no change is made to a remediated field, that remediated field remains NULL.
1104 -- ====================================================================================================
1105 CREATE TABLE module2.metro2_remediation_final AS
1106 WITH
1107 -- --------------------------------------------------------------------------------------------
1108 -- The date of account information describes a current-cycle account record. Historical
1109 -- PHP provides evidence for changing its fields only where treatment removed their basis.
1110 source_context AS (
1111     SELECT w.*,
1112            CASE w.account_status_17a WHEN '61' THEN 'J' WHEN '62' THEN 'G'
1113                WHEN '63' THEN 'K' WHEN '64' THEN 'L' WHEN '65' THEN 'H' END AS paid_major,
1114            (date_trunc('month',w.date_closed) - interval '1 month')::date AS preclosure_month,
1115            date_trunc('month',w.date_of_first_delinquency)::date AS source_onset_month,
1116            w.remediation_treatment IN ('SIMPLE_DELINQUENCY_PHP_CLEANUP','FULL_DEROGATORY_PHP_CLEANUP') AS cleanup
1117     FROM module2.metro2_remediation_window_eval w
1118 ),
1119 monthly_evidence AS (
1120     SELECT d.account,
1121            string_agg(d.remediated_status,'' ORDER BY d.byte_date DESC) AS proposed_php,
1122            max(d.original_status) FILTER (WHERE d.byte_date = s.php_left_byte_date) AS newest_mark,
1123            bool_or(d.byte_date = s.php_left_byte_date AND d.original_status <> d.remediated_status) AS newest_edited,
1124            max(d.byte_date) FILTER (WHERE d.original_status = s.paid_major
1125                AND d.original_status <> d.remediated_status) AS removed_paid_major_month,
1126            bool_or(d.remediated_status = s.paid_major) AS paid_major_survives,
1127            max(d.byte_date) FILTER (WHERE d.remediated_status IN ('1','2','3','4','5','6','G','H','J','K','L')) AS last_retained_adverse,
1128            max(d.original_status) FILTER (WHERE d.byte_date = s.preclosure_month) AS preclosure_mark,
1129            bool_or(d.byte_date = s.preclosure_month AND d.original_status <> d.remediated_status) AS preclosure_edited,
1130            max(d.byte_date) FILTER (WHERE d.original_status = 'D') AS last_original_unknown,
1131            max(d.byte_date) FILTER (WHERE d.original_status IN ('1','2','3','4','5','6','G','H','J','K','L')) AS last_original_adverse,
1132            -- Prove the documented onset in the original data. A cured or unknown
1133            -- intervening month cannot connect a prior episode to a newer correction.
1134            min(d.byte_date) FILTER (WHERE d.byte_date = s.source_onset_month
1135                AND d.original_status IN ('1','2','3','4','5','6')) AS observed_onset,
1136            min(d.byte_date) FILTER (WHERE d.byte_date >= s.source_onset_month
1137                AND d.original_status IN ('0','B','D')) AS first_episode_break
1138     FROM module2.metro2_remediation_php_detail d
1139     JOIN source_context s USING (account)
1140     GROUP BY d.account
1141 ),
1142 field_basis AS (
1143     SELECT s.*, m.proposed_php, m.newest_mark, m.newest_edited, m.removed_paid_major_month,
1144            m.paid_major_survives, m.last_retained_adverse, m.preclosure_mark, m.preclosure_edited,
1145            m.last_original_unknown, m.last_original_adverse,
1146            CASE WHEN m.observed_onset IS NOT NULL
1147                 THEN daterange(m.observed_onset, m.first_episode_break, '[)') END AS observed_episode,
1148            CASE m.newest_mark WHEN '0' THEN '11' WHEN '1' THEN '71' WHEN '2' THEN '78'
1149                WHEN '3' THEN '80' WHEN '4' THEN '82' WHEN '5' THEN '83' WHEN '6' THEN '84'
1150                WHEN 'G' THEN '93' WHEN 'H' THEN '94' WHEN 'J' THEN '95' WHEN 'K' THEN '96' WHEN 'L' THEN '97'
1151            END AS status_supported_by_latest,
1152            (s.payment_rating_17b IN ('1','2','3','4','5','6','G','L')
1153              AND m.preclosure_mark = s.payment_rating_17b AND m.preclosure_edited
1154              AND (m.last_retained_adverse IS NULL OR m.last_retained_adverse <= s.preclosure_month)
1155              AND (s.source_onset_month IS NULL OR s.source_onset_month <= s.preclosure_month)) AS closure_rating_removed
1156     FROM source_context s JOIN monthly_evidence m USING (account)
1157 ),
1158 candidate_basis AS (
1159     SELECT b.*,
1160            CASE
1161                WHEN NOT cleanup THEN NULL
1162                -- A paid-derogatory classification can change only after its corresponding
1163                -- original event was actually removed. Preserve a surviving or later basis.

1169                    AND (source_onset_month IS NULL OR source_onset_month <= removed_paid_major_month)
1170                    AND (payment_rating_17b IS NULL OR payment_rating_17b IN ('0',paid_major) OR closure_rating_removed)
1171                    THEN removed_paid_major_month

1176                WHEN newest_edited AND account_status_17a = status_supported_by_latest
1177                    AND (payment_rating_17b IS NULL OR payment_rating_17b IN ('0',newest_mark))
1178                    AND (source_onset_month IS NULL OR source_onset_month <= php_left_byte_date)

   1 /* ====================================================================================================
   2 PROGRAM:  Metro 2 Synthetic Portfolio Generator — (Version 2)
   3 SUBTITLE: Module 1: Longitudinal Tradeline Sample Builder
   4 FILE:     module_01_metro2_synthetic_portfolio_generator.sql
   5 AUTHOR:   Andrew R Goad
   6 DB:       PostgreSQL 15+
   7 PURPOSE:  Build a synthetic Metro 2-style portfolio for analytics, SQL learning, QA practice,
   8           GitHub portfolio use, and later remediation simulation modules.
   9 
  10 AUTHORING INTENT
  11 ----------------
  12 This script is written as BOTH:
  13 1) a working synthetic data generator, and
  14 2) a teaching tool for users who want to learn the SQL and methodology step by step.
  15 
  16 VERSION HISTORY
  17 ---------------
  18 Version 1:
  19 - Built metro2_sample first
  20 - Then repeatedly exploded PHP to derive stitched outputs
  21 - Included QA ideas, but the computational design was heavier than necessary
  22 
  23 Version 2:
  24 - Materializes month-level account performance once in metro2_status_history
  25 - Uses that table as the central truth source
  26 - Derives metro2_sample and metro2_final from the same reusable month-level history
  27 - Improves performance, readability, and auditability
  28 - Keeps QA in the same script now that the target environment is local PostgreSQL + DBeaver
  29 
  30 CORE DESIGN PRINCIPLE
  31 ---------------------
  32 PHP is an output artifact, not the computational backbone.
  33 
  34 This means:
  35 - We do NOT repeatedly explode and reassemble PHP to compute business logic
  36 - Instead, we compute a clean month-level status history first
  37 - Then PHP becomes a rendered view over that history
  38 
  39 This is both:
  40 - more efficient
  41 - easier to debug
  42 - easier to explain to future readers
  43 
  44 ======================================================================================================
  45 JOB AID — HOW TO USE THIS SCRIPT
  46 ======================================================================================================
  47 
  48 1) INSTALL / ENVIRONMENT ASSUMPTION
  49    This script is intended for local PostgreSQL inside DBeaver.
  50    It is not optimized for browser sandboxes like DB Fiddle.
  51 
  52 2) RECOMMENDED DATABASE / SCHEMA SETUP
  53    Example:
  54       CREATE DATABASE metro2_lab;
  55       CREATE SCHEMA IF NOT EXISTS module1;
  56       SET search_path TO module1, public;
  57 
  58    This script creates the schema if needed and sets the search_path for the current session.
  59    Run the complete script as one unit. A validation or build error rolls back the refresh.
  60 
  61 3) INPUTS TO EDIT
  62    Most users should only edit the INSERT INTO module1_params statement near the top.
  63    Inputs:
  64       - sample_size
  65       - pct_current
  66       - pct_mild
  67       - pct_mod
  68       - pct_severe
  69       - pct_derog
  70 
  71    Defaults:
  72       sample_size = 5000000
  73       current     = 70%
  74       mild        = 15%
  75       mod         =  8%
  76       severe      =  4%
  77       derog       =  3%
  78 
  79 4) VALIDATION
  80    The script validates the user inputs and raises an error immediately if:
  81       - sample_size <= 0
  82       - any percentage is outside [0, 1]
  83       - percentages differ from 1.000000 by more than the accepted tolerance, 0.000001

  85 5) MAIN OUTPUT TABLES
  86    A) metro2_account_blueprint
  87       Account-level generation metadata
  88 
  89    B) metro2_status_history

  91       This is the core month-level truth table
  92 
  93    C) metro2_sample
  94       Longitudinal snapshot table with:
  95          - account
  96          - date_of_account_information
  97          - php
  98 
  99    D) metro2_final
 100       Final account-level output table with:
 101          - latest_doai
 102          - date_closed
 103          - full_php
 104          - account_status_17A
 105          - payment_rating_17B
 106          - date_of_first_delinquency
 107 
 108 6) QA / REVIEW
 109    The final section contains review queries to help inspect the output.
 110    These queries are intended for:

 112       - screenshots

 118 ======================================================================================================
 119

 122    - leftmost byte = most recent month represented

 138    4 = 120 DPD
 139    5 = 150 DPD
 140    6 = 180+ DPD

 142    H = foreclosure
 143    J = voluntary surrender
 144    K = repossession
 145    L = charge-off
 146 
 147 C) ACCOUNT STATUS 17A VALUES MODELED HERE
 148    11 = current
 149    13 = paid/closed account / zero balance
 150    61 = paid in full, surrender
 151    62 = paid in full, collection
 152    63 = paid in full, repossession
 153    64 = paid in full, charge-off
 154    65 = paid in full, foreclosure
 155    71 = 30–59 DPD
 156    78 = 60–89 DPD
 157    80 = 90–119 DPD

 165    97 = charge-off

 187 -- SECTION 0: SCHEMA SETUP
 188 -- ====================================================================================================
 189 -- Purpose:
 190 --   Keep project tables out of the default public schema and place them in a dedicated module schema.
 191 --
 192 -- Why this exists:
 193 --   A dedicated schema is cleaner, more professional, and easier to manage in DBeaver.
 194 --
 195 -- SQL mechanics:
 196 --   - CREATE SCHEMA IF NOT EXISTS creates the schema only if it does not already exist
 197 --   - SET search_path tells PostgreSQL where to create/find unqualified objects for this session
 198 -- ====================================================================================================
 199 BEGIN;
 200 CREATE SCHEMA IF NOT EXISTS module1;
 201 SET search_path TO module1, public;

 204 -- ====================================================================================================
 205 -- SECTION 1: RESET THE SESSION'S PARAMETER TABLE
 206 -- ====================================================================================================
 207 -- A permanent table with the same name in public or module1 belongs to its owner.
 208 DROP TABLE IF EXISTS pg_temp.module1_params;
 209 
 210 
 211 -- ====================================================================================================
 212 -- SECTION 2: USER PARAMETERS
 213 -- ====================================================================================================
 214 -- Purpose:
 215 --   Store user-editable controls for sample size and portfolio mix.
 216 --
 217 -- Why this exists:
 218 --   Putting parameters into a table makes them easy to:
 219 --   - inspect
 220 --   - validate
 221 --   - reference in later SQL blocks
 222 --
 223 -- SQL mechanics:
 224 --   - CREATE TEMP TABLE creates a temporary table that exists only in the current session
 225 --   - The INSERT statement below is the main user-editable configuration row
 226 -- ====================================================================================================
 227 CREATE TEMP TABLE pg_temp.module1_params (
 228     sample_size   INTEGER NOT NULL,
 229     pct_current   NUMERIC(12,6) NOT NULL,
 230     pct_mild      NUMERIC(12,6) NOT NULL,
 231     pct_mod       NUMERIC(12,6) NOT NULL,
 232     pct_severe    NUMERIC(12,6) NOT NULL,
 233     pct_derog     NUMERIC(12,6) NOT NULL
 234 );
 235 
 236 INSERT INTO pg_temp.module1_params (
 237     sample_size,
 238     pct_current,
 239     pct_mild,
 240     pct_mod,
 241     pct_severe,
 242     pct_derog
 243 )
 244 VALUES (
 245     5000000,   -- total number of synthetic accounts to generate
 246     0.700000,  -- share of CURRENT accounts
 247     0.150000,  -- share of MILD delinquency accounts
 248     0.080000,  -- share of MOD delinquency accounts
 249     0.040000,  -- share of SEVERE delinquency accounts
 250     0.030000   -- share of DEROG accounts
 251 );
 252 
 253 
 254 -- ====================================================================================================
 255 -- SECTION 3: GATEKEEPER VALIDATION
 256 -- ====================================================================================================
 257 -- Purpose:
 258 --   Fail fast if the parameter configuration is invalid.
 259 --
 260 -- Why this exists:
 261 --   Validation at the top prevents confusing downstream failures.
 262 --
 263 -- SQL mechanics:
 264 --   - DO $$ ... $$ runs a procedural PL/pgSQL block
 265 --   - We read the parameter row into variables
 266 --   - We test the values using IF statements
 267 --   - RAISE EXCEPTION stops the script immediately with a descriptive message
 268 -- ====================================================================================================
 269 DO $$
 270 DECLARE
 271     v_sample_size INTEGER;
 272     v_pct_current NUMERIC(12,6);
 273     v_pct_mild    NUMERIC(12,6);
 274     v_pct_mod     NUMERIC(12,6);
 275     v_pct_severe  NUMERIC(12,6);
 276     v_pct_derog   NUMERIC(12,6);
 277     v_sum         NUMERIC(18,10);
 278 BEGIN
 279     SELECT
 280         sample_size,
 281         pct_current,
 282         pct_mild,
 283         pct_mod,
 284         pct_severe,
 285         pct_derog
 286     INTO STRICT
 287         v_sample_size,
 288         v_pct_current,
 289         v_pct_mild,
 290         v_pct_mod,
 291         v_pct_severe,
 292         v_pct_derog
 293     FROM pg_temp.module1_params;
 294 
 295     v_sum := v_pct_current + v_pct_mild + v_pct_mod + v_pct_severe + v_pct_derog;
 296 
 297     IF v_sample_size IS NULL OR v_sample_size <= 0 THEN
 298         RAISE EXCEPTION
 299             'MODULE 1 PARAMETER VALIDATION FAILED: sample_size must be a positive integer. Current value = %',
 300             v_sample_size;
 301     END IF;
 302 
 303     IF v_pct_current < 0 OR v_pct_current > 1
 304        OR v_pct_mild  < 0 OR v_pct_mild  > 1
 305        OR v_pct_mod   < 0 OR v_pct_mod   > 1
 306        OR v_pct_severe < 0 OR v_pct_severe > 1
 307        OR v_pct_derog < 0 OR v_pct_derog > 1
 308     THEN
 309         RAISE EXCEPTION
 310             'MODULE 1 PARAMETER VALIDATION FAILED: all percentage inputs must be between 0 and 1 inclusive. Current values = current:% mild:% mod:% severe:% derog:%',
 311             v_pct_current, v_pct_mild, v_pct_mod, v_pct_severe, v_pct_derog;
 312     END IF;
 313 
 314     IF ABS(v_sum - 1.000000) > 0.000001 THEN
 315         RAISE EXCEPTION
 316             'MODULE 1 PARAMETER VALIDATION FAILED: profile percentages must sum to 1.000000 within 0.000001. Current sum = % (current:% mild:% mod:% severe:% derog:%)',
 317             v_sum, v_pct_current, v_pct_mild, v_pct_mod, v_pct_severe, v_pct_derog;
 318     END IF;
 319 END $$;

 321 -- Only after validation succeeds, replace this module's four persistent outputs.
 322 -- PostgreSQL restores the prior tables if a later step fails in this transaction.
 323 DROP TABLE IF EXISTS module1.metro2_final;
 324 DROP TABLE IF EXISTS module1.metro2_sample;
 325 DROP TABLE IF EXISTS module1.metro2_status_history;
 326 DROP TABLE IF EXISTS module1.metro2_account_blueprint;

 328 -- ====================================================================================================
 329 -- SECTION 4: BUILD ACCOUNT BLUEPRINT
 330 -- ====================================================================================================
 331 -- Purpose:
 332 --   Create one account-level row per synthetic account, including:
 333 --   - profile assignment
 334 --   - activity flag
 335 --   - closure behavior
 336 --   - derog code
 337 --   - date range
 338 --   - synthetic behavior pattern string
 339 --
 340 -- Why this exists:
 341 --   This table is the "account design layer" for the module.
 342 --   It lets us separate:
 343 --      (a) account-level assumptions
 344 --   from (b) month-level status generation
 345 --
 346 -- SQL mechanics:
 347 --   This section uses a chain of CTEs (WITH clauses).
 348 --   A CTE is like a temporary named result set used only within one query.
 349 --   We use CTEs here because each step builds logically on the prior step.
 350 -- ====================================================================================================
 351 CREATE TABLE module1.metro2_account_blueprint AS
 352 WITH
 353 -- --------------------------------------------------------------------------------------------
 354 -- CTE: params
 355 -- Purpose:
 356 --   Read the one-row parameter table into the query.
 357 --
 358 -- SQL mechanics:
 359 --   SELECT * FROM module1_params simply exposes the parameters for later CTEs.
 360 -- --------------------------------------------------------------------------------------------
 361 params AS (
 362     SELECT * FROM pg_temp.module1_params
 363 ),
 364 
 365 -- --------------------------------------------------------------------------------------------
 366 -- CTE: profile_cutoffs
 367 -- Purpose:
 368 --   Convert percentage targets into cumulative integer cutoffs.
 369 --
 370 -- Why this exists:
 371 --   We want to assign account ids 1..N into profile buckets according to the user-configured mix.
 372 --
 373 -- SQL mechanics:
 374 --   - FLOOR(sample_size * pct_x) converts percentages into counts
 375 --   - thresholds use cumulative floors. The final bucket receives the remaining IDs.
 376 --   - a later rare-pattern override can change the final profile label. Resizing the study can move an ID into another bucket.
 377 -- --------------------------------------------------------------------------------------------
 378 profile_cutoffs AS (
 379     SELECT
 380         sample_size,
 381         FLOOR(sample_size * pct_current)::INT AS curr_cut,
 382         LEAST(sample_size, FLOOR(sample_size * (pct_current + pct_mild)))::INT AS mild_cut,
 383         LEAST(sample_size, FLOOR(sample_size * (pct_current + pct_mild + pct_mod)))::INT AS mod_cut,
 384         LEAST(sample_size, FLOOR(sample_size * (pct_current + pct_mild + pct_mod + pct_severe)))::INT AS severe_cut
 385     FROM params
 386 ),
 387 
 388 -- --------------------------------------------------------------------------------------------
 389 -- CTE: base_accounts
 390 -- Purpose:
 391 --   Create one row per synthetic account and assign a base profile type.
 392 --
 393 -- Why this exists:
 394 --   This is the first true account-level population step.
 395 --
 396 -- SQL mechanics:
 397 --   - generate_series(1, sample_size) creates integers 1..sample_size
 398 --   - each integer becomes an account id
 399 --   - CASE compares each account id to the cumulative cutoffs to assign its profile bucket
 400 -- --------------------------------------------------------------------------------------------
 401 base_accounts AS (
 402     SELECT
 403         gs AS account,
 404         CASE
 405             WHEN gs <= pc.curr_cut   THEN 'CURRENT'
 406             WHEN gs <= pc.mild_cut   THEN 'MILD'
 407             WHEN gs <= pc.mod_cut    THEN 'MOD'
 408             WHEN gs <= pc.severe_cut THEN 'SEVERE'
 409             ELSE 'DEROG'
 410         END AS base_profile_type
 411     FROM profile_cutoffs pc
 412     CROSS JOIN generate_series(1, (SELECT sample_size FROM params)) AS gs
 413 ),
 414 
 415 -- --------------------------------------------------------------------------------------------
 416 -- CTE: seeds
 417 -- Purpose:
 418 --   Create deterministic pseudo-random seed values per account.
 419 --
 420 -- Why this exists:
 421 --   We want reproducible synthetic variation. If you rerun the script with the same inputs,
 422 --   each account should get the same synthetic behavior.
 423 --
 424 -- SQL mechanics:
 425 --   - md5(text) produces a deterministic hash string
 426 --   - substr(..., 1, 7) takes part of the hash
 427 --   - the hex is converted into an integer using bit casting
 428 --   - the eight suffixes select separate deterministic streams; seven hex digits range from zero through 268435455
 429 -- --------------------------------------------------------------------------------------------
 430 seeds AS (
 431     SELECT
 432         b.*,
 433         (('x' || substr(md5(account::text || '-a'), 1, 7))::bit(28)::int) AS s1,
 434         (('x' || substr(md5(account::text || '-b'), 1, 7))::bit(28)::int) AS s2,
 435         (('x' || substr(md5(account::text || '-c'), 1, 7))::bit(28)::int) AS s3,
 436         (('x' || substr(md5(account::text || '-d'), 1, 7))::bit(28)::int) AS s4,
 437         (('x' || substr(md5(account::text || '-e'), 1, 7))::bit(28)::int) AS s5,
 438         (('x' || substr(md5(account::text || '-f'), 1, 7))::bit(28)::int) AS s6,
 439         (('x' || substr(md5(account::text || '-g'), 1, 7))::bit(28)::int) AS s7,
 440         (('x' || substr(md5(account::text || '-h'), 1, 7))::bit(28)::int) AS s8
 441     FROM base_accounts b
 442 ),
 443 
 444 -- --------------------------------------------------------------------------------------------
 445 -- CTE: seeded
 446 -- Purpose:
 447 --   Convert the raw seed values into account-level features:
 448 --   - active vs inactive
 449 --   - behavior variant
 450 --   - suppression flag
 451 --   - derog code family
 452 --
 453 -- Why this exists:
 454 --   This is where account-level diversity begins.
 455 --
 456 -- SQL mechanics:
 457 --   - CASE + modulo (%) creates controlled deterministic branching
 458 --   - s1%100 gives a stable pseudo-random number from 0 to 99 for each account
 459 -- --------------------------------------------------------------------------------------------
 460 seeded AS (
 461     SELECT
 462         account,
 463         base_profile_type,
 464 
 465         CASE
 466             WHEN base_profile_type = 'CURRENT' THEN CASE WHEN s1 % 100 < 80 THEN 1 ELSE 0 END
 467             WHEN base_profile_type = 'MILD'    THEN CASE WHEN s1 % 100 < 70 THEN 1 ELSE 0 END
 468             WHEN base_profile_type = 'MOD'     THEN CASE WHEN s1 % 100 < 55 THEN 1 ELSE 0 END
 469             WHEN base_profile_type = 'SEVERE'  THEN CASE WHEN s1 % 100 < 38 THEN 1 ELSE 0 END
 470             ELSE                                    CASE WHEN s1 % 100 < 22 THEN 1 ELSE 0 END
 471         END AS active_flag,
 472 
 473         s2,
 474         s3,
 475         s4 % 100 AS behavior_variant,
 476 
 477         CASE WHEN s5 % 100 < 2 THEN 1 ELSE 0 END AS has_suppression,
 478         1 + (s6 % 8) AS suppression_start_age,
 479 
 480         CASE
 481             WHEN s7 % 100 < 50 THEN 'L'
 482             WHEN s7 % 100 < 75 THEN 'G'
 483             WHEN s7 % 100 < 87 THEN 'K'
 484             WHEN s7 % 100 < 95 THEN 'J'
 485             ELSE 'H'
 486         END AS derog_code,
 487 
 488         s8 AS raw_seed
 489     FROM seeds
 490 ),
 491 
 492 -- --------------------------------------------------------------------------------------------
 493 -- CTE: patterned
 494 -- Purpose:
 495 --   Propose an initial reporting window length per account.
 496 --
 497 -- Why this exists:
 498 --   Real portfolios have varied ages:
 499 --   - some accounts are new
 500 --   - some are seasoned
 501 --   - some are very old but still within bureau-detail retention assumptions
 502 --
 503 -- SQL mechanics:
 504 --   - nested CASE statements create different vintage distributions by profile type
 505 -- --------------------------------------------------------------------------------------------
 506 patterned AS (
 507     SELECT
 508         account,
 509         base_profile_type,
 510         active_flag,
 511         behavior_variant,
 512         has_suppression,
 513         suppression_start_age,
 514         derog_code,
 515         raw_seed,
 516         CASE
 517             WHEN base_profile_type = 'CURRENT' THEN
 518                 CASE
 519                     WHEN s2 % 100 < 20 THEN  3 + (s3 % 10)
 520                     WHEN s2 % 100 < 60 THEN 13 + (s3 % 24)
 521                     WHEN s2 % 100 < 85 THEN 37 + (s3 % 24)
 522                     ELSE                   61 + (s3 % 24)
 523                 END
 524             WHEN base_profile_type = 'MILD' THEN
 525                 CASE
 526                     WHEN s2 % 100 < 15 THEN  6 + (s3 % 7)
 527                     WHEN s2 % 100 < 60 THEN 13 + (s3 % 24)
 528                     WHEN s2 % 100 < 85 THEN 37 + (s3 % 24)
 529                     ELSE                   61 + (s3 % 24)
 530                 END
 531             WHEN base_profile_type = 'MOD' THEN
 532                 CASE
 533                     WHEN s2 % 100 < 20 THEN  8 + (s3 % 9)
 534                     WHEN s2 % 100 < 65 THEN 17 + (s3 % 20)
 535                     WHEN s2 % 100 < 88 THEN 37 + (s3 % 24)
 536                     ELSE                   61 + (s3 % 24)
 537                 END
 538             WHEN base_profile_type = 'SEVERE' THEN
 539                 CASE
 540                     WHEN s2 % 100 < 30 THEN 12 + (s3 % 13)
 541                     WHEN s2 % 100 < 75 THEN 25 + (s3 % 24)
 542                     ELSE                   49 + (s3 % 36)
 543                 END
 544             WHEN base_profile_type = 'DEROG' THEN
 545                 CASE
 546                     WHEN s2 % 100 < 25 THEN 18 + (s3 % 13)
 547                     WHEN s2 % 100 < 75 THEN 31 + (s3 % 24)
 548                     ELSE                   55 + (s3 % 30)
 549                 END
 550         END AS months_reporting_raw
 551     FROM seeded
 552 ),
 553 
 554 -- --------------------------------------------------------------------------------------------
 555 -- CTE: profile_logic
 556 -- Purpose:
 557 --   Convert a very small number of accounts into reversed-major-derog cases.
 558 --
 559 -- Why this exists:
 560 --   In real-world remediation and servicing scenarios, banks sometimes reverse major derogatory
 561 --   outcomes. We include a tiny number of those cases for realism and future remediation work.
 562 -- --------------------------------------------------------------------------------------------
 563 profile_logic AS (
 564     SELECT
 565         p.*,
 566         CASE
 567             WHEN base_profile_type IN ('CURRENT','MILD','MOD')
 568              AND active_flag = 1
 569              AND has_suppression = 0
 570              AND months_reporting_raw >= 20
 571              AND raw_seed % 100 < 2
 572             THEN 'REVERSED_MAJOR_DEROG'
 573             ELSE base_profile_type
 574         END AS profile_type
 575     FROM patterned p
 576 ),
 577 
 578 -- --------------------------------------------------------------------------------------------
 579 -- CTE: closure_logic
 580 -- Purpose:
 581 --   Assign some inactive accounts to paid/closed statuses.
 582 --
 583 -- Why this exists:
 584 --   A realistic portfolio should not contain only active and open derog accounts.
 585 --   It should also contain:
 586 --   - paid/closed current or near-current accounts
 587 --   - paid post-derog accounts (61–65)
 588 -- --------------------------------------------------------------------------------------------
 589 closure_logic AS (
 590     SELECT
 591         pl.*,
 592         CASE
 593             WHEN active_flag = 0
 594              AND profile_type IN ('CURRENT','MILD','MOD')
 595              AND raw_seed % 100 < 45
 596             THEN '13'
 597 
 598             WHEN active_flag = 0
 599              AND profile_type = 'DEROG'
 600              AND raw_seed % 100 < 55
 601             THEN CASE derog_code
 602                      WHEN 'J' THEN '61'
 603                      WHEN 'G' THEN '62'
 604                      WHEN 'K' THEN '63'
 605                      WHEN 'L' THEN '64'
 606                      WHEN 'H' THEN '65'
 607                      ELSE NULL
 608                  END
 609 
 610             ELSE NULL
 611         END AS close_status_code
 612     FROM profile_logic pl
 613 ),
 614 
 615 -- --------------------------------------------------------------------------------------------
 616 -- CTE: pattern_strings
 617 -- Purpose:
 618 --   Assign a behavior pattern string per account.
 619 --
 620 -- Why this exists:
 621 --   This is the core behavioral logic of the generator.
 622 --   Instead of generating month-to-month states independently, we use valid pattern strings
 623 --   so transitions remain logical.
 624 --
 625 -- SQL mechanics:
 626 --   - Each pattern string is ordered from most recent month to older months
 627 --   - Later we "place" that pattern into the account timeline
 628 -- --------------------------------------------------------------------------------------------
 629 pattern_strings AS (
 630     SELECT
 631         account,
 632         profile_type,
 633         active_flag,
 634         behavior_variant,
 635         has_suppression,
 636         suppression_start_age,
 637         derog_code,
 638         raw_seed,
 639         months_reporting_raw,
 640         close_status_code,
 641         CASE
 642             WHEN profile_type = 'REVERSED_MAJOR_DEROG'
 643                 THEN '012345' || derog_code || '543210'
 644 
 645             WHEN close_status_code = '13' THEN
 646                 CASE
 647                     WHEN behavior_variant < 70 THEN '0'
 648                     WHEN behavior_variant < 90 THEN '010'
 649                     ELSE '01210'
 650                 END
 651 
 652             WHEN close_status_code IN ('61','62','63','64','65') THEN
 653                 REPEAT(
 654                     CASE close_status_code
 655                         WHEN '61' THEN 'J'
 656                         WHEN '62' THEN 'G'
 657                         WHEN '63' THEN 'K'
 658                         WHEN '64' THEN 'L'
 659                         WHEN '65' THEN 'H'
 660                     END,
 661                     1 + LEAST(raw_seed % 4, 3)
 662                 ) || '6543210'
 663 
 664             WHEN profile_type = 'CURRENT' THEN
 665                 CASE
 666                     WHEN behavior_variant < 92 THEN '0'
 667                     WHEN behavior_variant < 98 THEN '010'
 668                     ELSE '01210'
 669                 END
 670 
 671             WHEN profile_type = 'MILD' THEN
 672                 CASE
 673                     WHEN behavior_variant < 30 THEN '10'
 674                     WHEN behavior_variant < 55 THEN '110'
 675                     WHEN behavior_variant < 75 THEN '210'
 676                     WHEN behavior_variant < 90 THEN '010'
 677                     ELSE '01210'
 678                 END
 679 
 680             WHEN profile_type = 'MOD' THEN
 681                 CASE
 682                     WHEN behavior_variant < 45 THEN '3210'
 683                     WHEN behavior_variant < 80 THEN '43210'
 684                     ELSE '0123210'
 685                 END
 686 
 687             WHEN profile_type = 'SEVERE' THEN
 688                 CASE
 689                     WHEN behavior_variant < 55 THEN '543210'
 690                     ELSE '6543210'
 691                 END
 692 
 693             WHEN profile_type = 'DEROG' THEN
 694                 REPEAT(
 695                     derog_code,
 696                     1 + LEAST(raw_seed % 5, 4)
 697                 ) || '6543210'
 698         END AS pattern_string
 699     FROM closure_logic
 700 ),
 701 
 702 -- --------------------------------------------------------------------------------------------
 703 -- CTE: pattern_meta
 704 -- Purpose:
 705 --   Derive metadata about each pattern:
 706 --   - pattern length
 707 --   - mode (NONE / ACTIVE / CURED / CLOSED)
 708 --   - clean runway requirement
 709 --
 710 -- Why this exists:
 711 --   Some patterns must be pushed farther back in time so the latest month is current.
 712 --   We also require clean history behind adverse ramps to avoid unrealistic thin-file behavior.
 713 -- --------------------------------------------------------------------------------------------
 714 pattern_meta AS (
 715     SELECT
 716         account,
 717         profile_type,
 718         active_flag,
 719         behavior_variant,
 720         has_suppression,
 721         suppression_start_age,
 722         derog_code,
 723         raw_seed,
 724         months_reporting_raw,
 725         close_status_code,
 726         pattern_string,
 727         LENGTH(pattern_string) AS pattern_length,
 728         CASE
 729             WHEN profile_type = 'REVERSED_MAJOR_DEROG' THEN 'CURED'
 730             WHEN close_status_code IS NOT NULL THEN 'CLOSED'
 731             WHEN profile_type IN ('SEVERE', 'DEROG') THEN 'ACTIVE'
 732             WHEN profile_type IN ('CURRENT','MILD','MOD')
 733                  AND pattern_string IN ('010','01210','0123210')
 734             THEN 'CURED'
 735             WHEN pattern_string = '0' THEN 'NONE'
 736             ELSE 'ACTIVE'
 737         END AS pattern_mode,
 738         CASE
 739             WHEN pattern_string = '0' THEN 0
 740             WHEN pattern_string IN ('10','110','010') THEN 2
 741             WHEN pattern_string IN ('210','01210') THEN 3
 742             WHEN pattern_string IN ('3210') THEN 3
 743             WHEN pattern_string IN ('43210','0123210') THEN 4
 744             WHEN pattern_string IN ('543210') THEN 5
 745             WHEN pattern_string IN ('6543210') THEN 6
 746             WHEN profile_type = 'REVERSED_MAJOR_DEROG' THEN 6
 747             ELSE 6
 748         END AS clean_runway
 749     FROM pattern_strings
 750 ),
 751 
 752 -- --------------------------------------------------------------------------------------------
 753 -- CTE: fitted
 754 -- Purpose:
 755 --   Force enough reporting history to fit the pattern and required clean runway.
 756 --
 757 -- Why this exists:
 758 --   Without this, you get unrealistic cases where the oldest reported month is already deeply delinquent.
 759 --
 760 -- SQL mechanics:
 761 --   - GREATEST ensures the account is old enough to fit:
 762 --         pattern_length + clean_runway
 763 --   - LEAST caps history at 84 months
 764 -- --------------------------------------------------------------------------------------------
 765 fitted AS (
 766     SELECT
 767         account,
 768         profile_type,
 769         active_flag,
 770         behavior_variant,
 771         has_suppression,
 772         suppression_start_age,
 773         derog_code,
 774         raw_seed,
 775         months_reporting_raw,
 776         close_status_code,
 777         pattern_string,
 778         pattern_length,
 779         pattern_mode,
 780         clean_runway,
 781         LEAST(
 782             GREATEST(months_reporting_raw, pattern_length + clean_runway),
 783             84
 784         ) AS months_reporting
 785     FROM pattern_meta
 786 ),
 787 
 788 -- --------------------------------------------------------------------------------------------
 789 -- CTE: dated
 790 -- Purpose:
 791 --   Assign account-level start and end dates.
 792 --
 793 -- Why this exists:
 794 --   Real portfolios are panel data. Accounts do not all start and stop on the same timeline.
 795 --
 796 -- SQL mechanics:
 797 --   - active accounts end at the anchor date
 798 --   - inactive accounts stop at a deterministic earlier date
 799 -- --------------------------------------------------------------------------------------------
 800 dated AS (
 801     SELECT
 802         account,
 803         profile_type,
 804         active_flag,
 805         behavior_variant,
 806         has_suppression,
 807         suppression_start_age,
 808         derog_code,
 809         raw_seed,
 810         months_reporting_raw,
 811         close_status_code,
 812         pattern_string,
 813         pattern_length,
 814         pattern_mode,
 815         clean_runway,
 816         months_reporting,
 817         CASE
 818             WHEN active_flag = 1 THEN DATE '2025-10-01'
 819             ELSE (DATE '2025-10-01' - ((1 + (account::bigint * 13 % 42)) * INTERVAL '1 month'))::date
 820         END AS end_date
 821     FROM fitted
 822 ),
 823 
 824 -- --------------------------------------------------------------------------------------------
 825 -- CTE: blueprint
 826 -- Purpose:
 827 --   Finalize the account-level blueprint table.
 828 --
 829 -- Why this exists:
 830 --   This is the one-row-per-account design table used by downstream steps.
 831 --
 832 -- SQL mechanics:
 833 --   - start_date is derived from end_date and months_reporting
 834 --   - date_closed is populated only for closed-status accounts
 835 --   - episode_start_age controls where the pattern is placed in the time series
 836 -- --------------------------------------------------------------------------------------------
 837 blueprint AS (
 838     SELECT
 839         account,
 840         profile_type,
 841         active_flag,
 842         months_reporting,
 843         (end_date - ((months_reporting - 1) * INTERVAL '1 month'))::date AS start_date,
 844         end_date,
 845         CASE WHEN close_status_code IS NOT NULL THEN end_date ELSE NULL END AS date_closed,
 846         close_status_code,
 847         has_suppression,
 848         suppression_start_age,
 849         derog_code,
 850         pattern_string,
 851         pattern_length,
 852         pattern_mode,
 853         clean_runway,
 854         CASE
 855             WHEN pattern_mode = 'NONE' THEN 0
 856             WHEN pattern_mode = 'ACTIVE' THEN 0
 857             WHEN profile_type = 'REVERSED_MAJOR_DEROG' THEN 0
 858             WHEN close_status_code IS NOT NULL THEN 0
 859             ELSE raw_seed % GREATEST(months_reporting - pattern_length - clean_runway + 1, 1)
 860         END AS episode_start_age
 861     FROM dated
 862 )
 863 SELECT
 864     account,
 865     profile_type,
 866     active_flag,
 867     months_reporting,
 868     start_date,
 869     end_date,
 870     date_closed,
 871     close_status_code,
 872     has_suppression,
 873     suppression_start_age,
 874     derog_code,
 875     pattern_string,
 876     pattern_length,
 877     pattern_mode,
 878     clean_runway,
 879     episode_start_age
 880 FROM blueprint
 881 ORDER BY account;
 882 
 883 CREATE UNIQUE INDEX ix_blueprint_account ON module1.metro2_account_blueprint (account);
 884

 886 -- ====================================================================================================
 887 -- SECTION 5: BUILD MONTH-LEVEL STATUS HISTORY
 888 -- ====================================================================================================
 889 -- Purpose:
 890 --   Create the central month-level truth table:
 891 --      metro2_status_history(account, byte_date, perf_age, status)
 892 --
 893 -- Why this exists:
 894 --   This is the biggest Version 2 optimization.
 895 --   Instead of deriving everything from PHP repeatedly, we calculate month-level history once.
 896 --
 897 -- SQL mechanics:
 898 --   - generate_series(start_date - 1 month, end_date - 1 month, 1 month)
 899 --     creates each represented performance month
 900 --   - ROW_NUMBER ordered descending by byte_date creates perf_age:
 901 --       0 = most recent represented month
 902 --       1 = one month older
 903 --   - pattern placement uses perf_age and episode_start_age
 904 -- ====================================================================================================
 905 CREATE TABLE module1.metro2_status_history AS
 906 WITH
 907 -- --------------------------------------------------------------------------------------------
 908 -- CTE: performance_months
 909 -- Purpose:
 910 --   Create one row per account per represented month.
 911 -- --------------------------------------------------------------------------------------------
 912 performance_months AS (
 913     SELECT
 914         a.account,
 915         a.profile_type,
 916         a.start_date,
 917         a.end_date,
 918         a.pattern_string,
 919         a.pattern_length,
 920         a.pattern_mode,
 921         a.episode_start_age,
 922         a.has_suppression,
 923         a.suppression_start_age,
 924         gs::date AS byte_date,
 925         ROW_NUMBER() OVER (
 926             PARTITION BY a.account
 927             ORDER BY gs DESC
 928         ) - 1 AS perf_age
 929     FROM module1.metro2_account_blueprint a
 930     CROSS JOIN LATERAL generate_series(
 931         a.start_date - INTERVAL '1 month',
 932         a.end_date   - INTERVAL '1 month',
 933         INTERVAL '1 month'
 934     ) AS gs
 935 ),
 936 
 937 -- --------------------------------------------------------------------------------------------
 938 -- CTE: status_history_raw
 939 -- Purpose:
 940 --   Translate each account’s pattern string into raw month-level statuses.
 941 --
 942 -- SQL mechanics:
 943 --   - If the account has no meaningful pattern, assign 0
 944 --   - If perf_age falls inside the pattern window, pull the corresponding character
 945 --     from pattern_string using SUBSTRING
 946 --   - Otherwise assign 0
 947 -- --------------------------------------------------------------------------------------------
 948 status_history_raw AS (
 949     SELECT
 950         p.account,
 951         p.byte_date,
 952         p.perf_age,
 953         CASE
 954             WHEN p.pattern_mode = 'NONE' THEN '0'
 955             WHEN p.perf_age BETWEEN p.episode_start_age
 956                                AND     p.episode_start_age + p.pattern_length - 1
 957             THEN SUBSTRING(
 958                     p.pattern_string
 959                     FROM ((p.perf_age - p.episode_start_age + 1)::int)
 960                     FOR 1
 961                  )
 962             ELSE '0'
 963         END AS status,
 964         p.has_suppression,
 965         p.suppression_start_age
 966     FROM performance_months p
 967 )
 968 
 969 -- --------------------------------------------------------------------------------------------
 970 -- Final SELECT for metro2_status_history
 971 -- Purpose:
 972 --   Overlay suppression after raw pattern logic is created.
 973 --
 974 -- Why this exists:
 975 --   This original D means payment history was unavailable to the study. It supplies no evidence of current performance.
 976 -- --------------------------------------------------------------------------------------------
 977 SELECT
 978     account,
 979     byte_date,
 980     perf_age,
 981     CASE
 982         WHEN has_suppression = 1
 983          AND perf_age BETWEEN suppression_start_age AND suppression_start_age + 1
 984         THEN 'D'
 985         ELSE status
 986     END AS status
 987 FROM status_history_raw
 988 ORDER BY account, byte_date DESC;
 989 
 990 CREATE UNIQUE INDEX ix_status_history_account_byte_date
 991     ON module1.metro2_status_history (account, byte_date DESC);
 992 
 993 
 994 -- ====================================================================================================
 995 -- SECTION 6: BUILD LONGITUDINAL SNAPSHOT TABLE
 996 -- ====================================================================================================
 997 -- Purpose:
 998 --   Create the synthetic ingestion dataset:
 999 --      account, date_of_account_information, php
1000 --
1001 -- Why this exists:
1002 --   This mimics the kind of monthly tradeline snapshot input your later remediation module will use.
1003 --
1004 -- SQL mechanics:
1005 --   - snapshot_rows creates each account’s DOAI timeline
1006 --   - snapshot_bytes expands each DOAI into 24 represented byte months
1007 --   - LEFT JOIN to metro2_status_history pulls the month-level status if it exists
1008 --   - COALESCE(..., 'B') fills missing older months with B
1009 --   - STRING_AGG assembles the 24 bytes into one PHP string
1010 -- ====================================================================================================
1011 CREATE TABLE module1.metro2_sample AS
1012 WITH
1013 -- --------------------------------------------------------------------------------------------
1014 -- CTE: snapshot_rows
1015 -- Purpose:
1016 --   Create one row per account per DOAI.
1017 -- --------------------------------------------------------------------------------------------
1018 snapshot_rows AS (
1019     SELECT
1020         a.account,
1021         gs::date AS date_of_account_information
1022     FROM module1.metro2_account_blueprint a
1023     CROSS JOIN LATERAL generate_series(
1024         a.start_date,
1025         a.end_date,
1026         INTERVAL '1 month'
1027     ) AS gs
1028 ),
1029 
1030 -- --------------------------------------------------------------------------------------------
1031 -- CTE: snapshot_bytes
1032 -- Purpose:
1033 --   Expand each DOAI into 24 PHP byte positions.
1034 --
1035 -- SQL mechanics:
1036 --   - generate_series(1,24) creates the 24 byte positions
1037 --   - byte_date = DOAI - pos months
1038 --   - because byte 1 is one month prior to DOAI in this project
1039 -- --------------------------------------------------------------------------------------------
1040 snapshot_bytes AS (
1041     SELECT
1042         s.account,
1043         s.date_of_account_information,
1044         pos,
1045         (s.date_of_account_information - (pos * INTERVAL '1 month'))::date AS byte_date
1046     FROM snapshot_rows s
1047     CROSS JOIN generate_series(1, 24) AS pos
1048 )
1049 
1050 -- --------------------------------------------------------------------------------------------
1051 -- Final SELECT for metro2_sample
1052 -- Purpose:
1053 --   Assemble a 24-byte PHP for every account / DOAI row.
1054 --
1055 -- SQL mechanics:
1056 --   - LEFT JOIN finds the underlying month-level status
1057 --   - COALESCE fills missing history with B
1058 --   - STRING_AGG(... ORDER BY pos) assembles bytes from left to right
1059 -- --------------------------------------------------------------------------------------------
1060 SELECT
1061     b.account,
1062     b.date_of_account_information,
1063     STRING_AGG(COALESCE(h.status, 'B'), '' ORDER BY b.pos) AS php
1064 FROM snapshot_bytes b
1065 LEFT JOIN module1.metro2_status_history h
1066     ON h.account = b.account
1067    AND h.byte_date = b.byte_date
1068 GROUP BY b.account, b.date_of_account_information
1069 ORDER BY b.account, b.date_of_account_information DESC;
1070 
1071 CREATE UNIQUE INDEX ix_sample_account_doai
1072     ON module1.metro2_sample (account, date_of_account_information DESC);
1073 
1074 
1075 -- ====================================================================================================
1076 -- SECTION 7: BUILD FINAL ACCOUNT-LEVEL OUTPUT
1077 -- ====================================================================================================
1078 -- Purpose:
1079 --   Produce one row per account with stitched history and latest-state Metro 2 fields.
1080 --
1081 -- Why this exists:
1082 --   This is the main output table for downstream review and future remediation modules.
1083 --
1084 -- Major improvement vs Version 1:
1085 --   We derive this table directly from metro2_status_history rather than re-exploding metro2_sample.
1086 -- ====================================================================================================
1087 CREATE TABLE module1.metro2_final AS
1088 WITH
1089 -- --------------------------------------------------------------------------------------------
1090 -- CTE: latest_status
1091 -- Purpose:
1092 --   Find the most recent represented status byte for each account.
1093 --
1094 -- SQL mechanics:
1095 --   - DISTINCT ON (account) keeps only the first row per account
1096 --   - ORDER BY account, byte_date DESC ensures the first row is the newest byte_date
1097 -- --------------------------------------------------------------------------------------------
1098 latest_status AS (
1099     SELECT DISTINCT ON (account)
1100         account,
1101         byte_date AS php_left_byte_date,
1102         status AS latest_byte
1103     FROM module1.metro2_status_history
1104     ORDER BY account, byte_date DESC
1105 ),
1106 
1107 -- --------------------------------------------------------------------------------------------
1108 -- CTE: full_timeline
1109 -- Purpose:
1110 --   Stitch each account’s full month-level history into one long PHP-like string.
1111 --
1112 -- Why this exists:
1113 --   This gives a deduplicated, most-recently-reported timeline for each account.
1114 -- --------------------------------------------------------------------------------------------
1115 full_timeline AS (
1116     SELECT
1117         account,
1118         STRING_AGG(status, '' ORDER BY byte_date DESC) AS full_php,
1119         MAX(byte_date) AS php_left_byte_date,
1120         MIN(byte_date) AS php_right_byte_date
1121     FROM module1.metro2_status_history
1122     GROUP BY account
1123 ),
1124 
1125 -- --------------------------------------------------------------------------------------------
1126 -- CTE: latest_doai
1127 -- Purpose:
1128 --   Define the latest reporting date per account.
1129 --
1130 -- Why this exists:
1131 --   In this module, latest_doai aligns to the blueprint end_date.
1132 -- --------------------------------------------------------------------------------------------
1133 latest_doai AS (
1134     SELECT
1135         account,
1136         end_date AS latest_doai
1137     FROM module1.metro2_account_blueprint
1138 ),
1139 
1140 -- --------------------------------------------------------------------------------------------
1141 -- CTE: ordered_status
1142 -- Purpose:
1143 --   Create a sequence over each account’s month-level history for DOFD analysis.
1144 --
1145 -- Why this exists:
1146 --   To derive a simple current adverse run, we need to identify the contiguous adverse segment
1147 --   from the most recent month backward until a non-adverse month appears.
1148 --
1149 -- SQL mechanics:
1150 --   - ROW_NUMBER creates a descending sequence
1151 --   - SUM(CASE...) as a window function counts non-adverse months seen so far
1152 --   - while non_adverse_seen = 0, we are still inside the initial adverse run
1153 -- --------------------------------------------------------------------------------------------
1154 ordered_status AS (
1155     SELECT
1156         h.account,
1157         h.byte_date,
1158         h.status,
1159         ROW_NUMBER() OVER (PARTITION BY h.account ORDER BY h.byte_date DESC) AS seq,
1160         SUM(
1161             CASE
1162                 WHEN h.status NOT IN ('1','2','3','4','5','6','G','H','J','K','L')
1163                 THEN 1 ELSE 0
1164             END
1165         ) OVER (
1166             PARTITION BY h.account
1167             ORDER BY h.byte_date DESC
1168             ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
1169         ) AS non_adverse_seen
1170     FROM module1.metro2_status_history h
1171 ),
1172 
1173 -- --------------------------------------------------------------------------------------------
1174 -- CTE: current_adverse_run
1175 -- Purpose:
1176 --   Find the first delinquency date inside the current contiguous adverse run.
1177 --
1178 -- Important methodology note:
1179 --   This is a simplified synthetic DOFD logic for a learning module.
1180 --   It is not a full production furnishing engine.
1181 --
1182 -- SQL mechanics:
1183 --   - Restrict to rows where non_adverse_seen = 0
1184 --     meaning we have not yet encountered a current/non-adverse break
1185 --   - Only numeric delinquency (1–6) supplies a date. A run of major codes alone can yield NULL.
1186 --   - An original D interrupts this synthetic run; an incomplete history cannot establish a real-world DOFD.
1187 -- --------------------------------------------------------------------------------------------
1188 current_adverse_run AS (
1189     SELECT
1190         account,
1191         MIN(byte_date) FILTER (WHERE status IN ('1','2','3','4','5','6')) AS date_of_first_delinquency
1192     FROM ordered_status
1193     WHERE non_adverse_seen = 0
1194     GROUP BY account
1195 ),
1196 
1197 -- --------------------------------------------------------------------------------------------
1198 -- CTE: joined
1199 -- Purpose:
1200 --   Bring together all intermediate pieces needed for the final select.
1201 -- --------------------------------------------------------------------------------------------
1202 joined AS (
1203     SELECT
1204         b.account,
1205         b.profile_type,
1206         d.latest_doai,
1207         b.date_closed,
1208         f.full_php,
1209         f.php_left_byte_date,
1210         f.php_right_byte_date,
1211         l.latest_byte,
1212         c.date_of_first_delinquency,
1213         b.close_status_code
1214     FROM module1.metro2_account_blueprint b
1215     JOIN latest_doai d USING (account)
1216     JOIN full_timeline f USING (account)
1217     JOIN latest_status l USING (account)
1218     LEFT JOIN current_adverse_run c USING (account)
1219 )
1220 
1221 -- --------------------------------------------------------------------------------------------
1222 -- Final SELECT for metro2_final
1223 -- Purpose:
1224 --   Model 17A as of latest_doai. The generator uses the previous month’s PHP as a proxy when current-cycle servicing data is unavailable.
1225 --
1226 -- Business logic:
1227 --   - close_status_code takes precedence over latest_byte when the account is closed
1228 --   - a latest original D on an open account supplies no 17A, 17B or DOFD under the generator rules
1229 --   - DOFD describes the active adverse run. Consumer Information Indicators and their Field 25 exceptions are outside these synthetic inputs.
1230 -- --------------------------------------------------------------------------------------------
1231 SELECT
1232     account,
1233     profile_type,
1234     latest_doai,
1235     date_closed,
1236     full_php,
1237     php_left_byte_date,
1238     php_right_byte_date,
1239 
1240     CASE
1241         WHEN close_status_code IS NOT NULL THEN close_status_code
1242         ELSE
1243             CASE latest_byte
1244                 WHEN '0' THEN '11'
1245                 WHEN '1' THEN '71'
1246                 WHEN '2' THEN '78'
1247                 WHEN '3' THEN '80'
1248                 WHEN '4' THEN '82'
1249                 WHEN '5' THEN '83'
1250                 WHEN '6' THEN '84'
1251                 WHEN 'G' THEN '93'
1252                 WHEN 'H' THEN '94'
1253                 WHEN 'J' THEN '95'
1254                 WHEN 'K' THEN '96'
1255                 WHEN 'L' THEN '97'
1256                 ELSE NULL
1257             END
1258     END AS account_status_17A,
1259 
1260     CASE
1261         WHEN close_status_code = '13' THEN '0'
1262         WHEN close_status_code IN ('61','62','63','64','65') THEN NULL
1263         ELSE
1264             CASE latest_byte
1265                 WHEN '0' THEN '0'
1266                 WHEN '1' THEN '1'
1267                 WHEN '2' THEN '2'
1268                 WHEN '3' THEN '3'
1269                 WHEN '4' THEN '4'
1270                 WHEN '5' THEN '5'
1271                 WHEN '6' THEN '6'
1272                 WHEN 'G' THEN 'G'
1273                 WHEN 'L' THEN 'L'
1274                 ELSE NULL
1275             END
1276     END AS payment_rating_17B,
1277 
1278     CASE
1279         WHEN close_status_code IS NOT NULL THEN NULL
1280         WHEN latest_byte IN ('1','2','3','4','5','6','G','H','J','K','L')
1281         THEN date_of_first_delinquency
1282         ELSE NULL
1283     END AS date_of_first_delinquency
1284 
1285 FROM joined
1286 ORDER BY account;
1287 
1288 CREATE UNIQUE INDEX ix_final_account
1289     ON module1.metro2_final (account);

Start with a local test database

Extract the PowerShell kit and open a PowerShell terminal in the folder containing src, tools and explorer-template. You need a running PostgreSQL server, its psql client, and a login that can create a database. The account explorer also uses Python 3. The example assumes the Windows Python launcher py -3. On a system with python3, use that command instead.

The launcher creates a fresh database and result folder for each run. It generates original monthly payment histories, assigns a bank issue, evaluates the credit-impact period and checks the proposed actions against the original evidence. The kit’s tools/RUN_STUDY.md covers connection settings, retained runs and monthly follow-up.

Choose a strategy and run it

Start with 1,000 accounts. Three consecutive original current months after the issue is the portfolio’s reference rule. The command opens a local explorer containing the accounts from this run. Edit the connection settings to match your test server.

$ErrorActionPreference = 'Stop'
$dbUser = 'postgres'
$dbServer = 'localhost'
$dbPort = 5432
$out = Join-Path $PWD ("metro2-run-" + [guid]::NewGuid().ToString("N"))
& ./tools/Run-Metro2Study.ps1 -AccountCount 1000 -CureMonths 3 -User $dbUser -Server $dbServer -Port $dbPort -OutputDirectory $out

$receipt = Join-Path $out 'run.json'
$study = Get-Content -Raw -LiteralPath $receipt | ConvertFrom-Json
$view = Join-Path $out 'explorer'
Copy-Item -LiteralPath ./explorer-template -Destination $view -Recurse
py -3 ./tools/build_explorer.py --database $study.database --host $study.server --port $study.port --user $dbUser --run-receipt $receipt --source-kind replay --output (Join-Path $view 'data.js')
if ($LASTEXITCODE -eq 0) { Invoke-Item (Join-Path $view 'index.html') }

Look for Verified in the launcher output. Open run.json to confirm the database, account count, rule and executed SQL hashes. The explorer’s source label and account count should agree. For a second trial, keep the same account count and change only the cure threshold. For a monthly follow-up, reuse that study’s saved module_02_configured.sql and original bank-issue dates. The engine checks the saved cure threshold before replacing a decision. To compare policies, launch a separate study.

Measured experiment · 1,000 synthetic accounts

What did one more month change?

Both runs use the same 35,395 original account-months and the same bank-issue dates. Requiring a fourth current month gave fewer accounts a confirmed cure by their reporting cutoff. In some cases a later delinquency entered the correction window.

Account 57 stays in review one more month

Its bank issue ran from May 2024 through June 2025. July, August and September were originally current. At the October 1 cutoff, three months confirm a July cure and close review. Four months leave the case open through September. The reviewer needs October performance from the November 1 snapshot. Both rules correct the same September 2024 late mark. Inspect account 57 in the three-month study

Why account 975 receives the extra deletion proposal

The bank issue ran from September 2023 through November 2024. The customer was current in December, January and February, fell behind in March 2025, and reached charge-off in September. Both runs see exactly that history on October 1.

Cure requirementWhat the bank could conclude
Three current monthsThe February mark, visible March 1, confirms cure effective December 2024. The credit-impact period ends in November. The September charge-off falls outside the window and the bank keeps the tradeline as reported.
Four current monthsMarch’s delinquency interrupts the streak. Credit impact extends through September. The latest severe event has no observed reversal at the cutoff, so the bank proposes deleting the tradeline.

Neither run substitutes an individual history entry on 975. Changing the policy changes which event qualifies for action. Compare your two runs account by account

From the extracted kit, point the comparison script to the two local explorers. Use full exports from the current kit, each created with its own native run receipt. The comparison checks the recorded SHA-256 digest of the export’s accounts and metadata, account and month totals, threshold and configured engine identity, then matches the original evidence across the two runs. Older viewers remain readable. Re-export their retained databases with the matching source materials for a new comparison. Supply the actual result-folder names.

py -3 ./tools/compare_study_thresholds.py ./first-run/explorer/data.js ./second-run/explorer/data.js --output ./threshold-comparison.json

Take a decision to a reviewer

Explain a change
Open an account in your local explorer. Identify the first and last bank-issue months, the latest observable history month, the proposed field changes and the earliest month a reviewer could confirm cure.
Assign the next action
manual_review_handoff.xlsx gives the monthly reviewer the next evidence to request. account_field_review.csv sends disputed fields or missing required ratings to servicing. field25_source_exceptions.csv identifies a missing date when a represented field condition already requires it.
Reproduce the decision
Keep totals.csv, outcomes.csv, run.json and policy_audit.json with the configured SQL and the comparison. A synthetic proposal can support a pre-production strategy decision. Live remediation also needs servicing evidence, current furnishing specifications, delivery records and bureau reconciliation.

Already have synthetic results in DBeaver? The export kit reads the existing tables. Point it to a copy of the viewer so you can keep your saved study. When testing imported data, also check rating values against the applicable specification. A nonblank unsupported rating such as X or D at status 13 can bypass the missing-rating queue.
